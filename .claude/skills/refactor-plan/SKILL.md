# リファクタリング計画書の作成

対象: `$ARGUMENTS`（未指定なら対象パスをユーザーに確認してから開始する）

今回は計画のみ。**コードは1文字も変更しない。**
実行は別のAIに任せるため、合格条件は「この計画書とコードだけを渡された実行者が、迷わず安全に作業を完遂できること」。

## 進め方
1. コード全体を読み、構造マップを作る（主要ファイルの役割と依存関係）
2. 問題を洗い出す（重複/巨大関数/責務混在/デッドコード/命名不統一/エラー処理の穴/直値の散在）
3. 効果×リスクで優先順位をつけ、作業項目に分解する
4. 完成した計画を実行順に頭からトレースし、前の項目の変更が後の項目の前提を壊さないか検証してから提出する

## 計画書の構成
1. **現状理解**: このコードが何をどう実現しているか（実行者への文脈共有を兼ねる）
2. **安全網の構築**（項目0として最初に実行させる）
   - 作業前コミットの手順
   - ベースライン確認の方法。テストがない場合は「どの動作を・どんな入力と期待出力で
     固定するか」の特性テスト仕様を、実行者がそのままテストコードにできる粒度で書く
3. **作業項目リスト**（実行順）。各項目に必ず含める:
   - ID/対象箇所（ファイルパス:行範囲）
   - 何が問題か（1〜2行）
   - どう変えるか（具体的に。判断が入りうる箇所は変更前後のコードスケッチをつける）
   - 完了条件（実行するコマンドと期待結果。テストなら対象テスト名まで）
   - リスクと、失敗した場合の戻し方
   - 依存: 先に完了している必要がある項目のID
4. **やらないことリスト**（機能追加・仕様変更・依存ライブラリ更新など、
   実行者が善意で逸脱しそうなことを先回りで禁止する）
5. **実行者への指示文**（計画書を渡すときそのままコピペできる形。
   「1項目ずつ実施・1項目ごとにコミット・完了条件を満たせなければ中断して報告」を含める）

## 品質基準
- 実行者はこの計画書とコード以外の文脈を持たない。あなたの頭の中の前提をすべて書き出す
- 1項目=1コミットで、独立に完了検証できる粒度に割る
- 「◯◯を整理する」のような、実行者の解釈が必要な表現を作業項目に残さない
